# Correct the spine cycle mean before tuning walk flow

The driver sees a rigid walk body and asks for gentle shoulder/spine response. Investigation found a concrete bug first: `new THREE.Vector4()` starts at `(0,0,0,1)`, so the runtime quaternion average adds an identity quaternion with weight1. The supposed cycle mean shifts the resting pose and drifts with total gait weight. Damping should reduce oscillation around the authored mean, not invent a different mean posture.

Make one runtime correction: initialize the weighted sum to `(0,0,0,0)`. Preserve every existing movement, cadence, suspension, contact, bank and head parameter. Do not add a legacy average path. The exploratory walk-specific tunable was removed before any commit or main merge; it hid this bug by bypassing damping, so it is not the current solution. Revisit authored walk motion only after inspecting the corrected baseline.

Opus confirms the bug and recommends this isolated fix. Verify actual single-gait runtime output against the source mean at weights .25/.5/1; compare main and corrected rigs with spineFlex1 (zero damping); inspect cycle-average body/head posture and contacts across all gaits. Use four phases at30/60/120Hz, starts/stops, both blend bands and both turn directions. Check zero-support windows because lower shoulders can trigger early contact. GPU side/three-quarter walk/trot/run plus live actions remain mandatory before main adoption, with Opus critique and one follow-up review. No solver statistic constitutes a visual pass.
